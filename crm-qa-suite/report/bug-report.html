Bugs

BUG-01Medium Backend

A null byte in the search query returns HTTP 500

Search (contacts, companies, deals, files)
Steps
GET /api/crm/v1/contacts?q=a%00b (same on /companies, /deals, /files)
Expected
400 validation error, or the search ignores the character.
Actual
500 internal_error. Other special characters (% \ ( [ * $ quotes, newlines) are handled fine. The UI search box would show a generic failure.
Suggested fix
Strip or reject U+0000 in query-string params before they reach the database layer.
BUG-02Medium Frontend

Expired session on submit shows a raw API message and leaves the dialog open

Session handling
Steps
Sign in, open Pipelines > New pipeline, fill the form, clear cookies (or let the session expire), press Create pipeline.
Expected
Redirect to /login?next=... or a clear 'Your session expired, sign in again' message that keeps the draft.
Actual
Dialog stays open and shows 'A secret API key or Dashboard session is required' (developer wording). No sign-in prompt. Reloading goes to the login page and the draft is lost. A normal page load redirects correctly.
Suggested fix
Handle 401 from the API client centrally: redirect to login with next=, and show a user-facing message.

BUG-08Low Backend

Control characters are accepted and stored in names

All string fields
Steps
POST /pipelines {"name":"a\u0000b","stages":[{"name":"s"}]} also "\n", "\r\nX-Evil: 1", "\u0001"
Expected
400 for control characters in single-line fields.
Actual
201, stored verbatim. The UI renders them safely, but logs, CSV exports and other tools can be confused.
Suggested fix
Reject or strip control characters (U+0000-U+001F, U+007F) in single-line fields.
BUG-09Low Backend

Invalid UTF-8 is accepted and silently replaced

Request parsing
Steps
POST /pipelines with raw body bytes {"name":"\xff\xfe",...} and content-type application/json
Expected
400 'body is not valid UTF-8'.
Actual
201; the name is stored as two U+FFFD replacement characters. A lone surrogate becomes three.
Suggested fix
Decode strictly (fatal on invalid sequences).
BUG-10Low Backend

The 120-character name limit counts UTF-16 units, not characters

Validation
Steps

Expected
Accepted: 100 characters is under the 120 limit.
Actual
400 'Too big: expected string to have <=120 characters' (the string is 200 UTF-16 units).

Count code points (or grapheme clusters), not string length.
BUG-11Low Backend

Oversized request bodies sometimes get an empty 502 instead of 413

Proxy / API
Steps
POST a 10 MB JSON body to /pipelines several times. Observed once in about 5 attempts. The limit sits between 1 MB and 2 MB.
Expected
Always 413 with the JSON error body.
Actual
Usually 413; intermittently an empty 502 from the proxy (the app closes the connection while the client is still uploading). The service stays healthy.
Suggested fix
Reject on Content-Length before reading the body, or drain the request before closing.

BUG-13Low Hardening

text/plain bodies are parsed as JSON; mutating calls without an Origin header are accepted

Request handling
Steps
POST /pipelines with content-type: text/plain and a JSON body -> 201. Also a session-cookie POST with no Origin header -> 201.
Expected
415 for non-JSON content types; ideally an Origin/Sec-Fetch-Site check on cookie-authenticated writes.
Actual
Accepted. Not exploitable today because the required crm-* headers force a CORS preflight, but it removes a layer of CSRF protection. (The login endpoint is protected and rejects cross-site requests.)
Suggested fix
Require application/json on write endpoints; check Origin/Sec-Fetch-Site for cookie sessions.

Design questions

Not defects as such. Each needs a product decision on whether the current behaviour is intended.

  • D-1 Duplicates are allowed everywherePipelines (even differing only by case), contacts (same email in any case), companies and close-reason labels can be duplicated. Three parallel creates of the same pipeline name made three pipelines. Stage names within a pipeline and close-reason codes ARE unique. Decide which should be unique, for example contact email.
  • D-2 Stages can be added to an archived pipelineThe page says an archived pipeline 'takes no new deals', but its stages can still be changed.
  • D-3 Import cannot update existing recordsonDuplicate supports only 'create' (default) and 'reject'. A re-import always creates duplicates unless reject is used; there is no update or skip mode.
  • D-4 Archiving with dependants is allowedA pipeline with open deals, and a company with contacts and deals, can be archived. Deleting them is correctly blocked with 409.
  • D-5 Moving a deal to its current stage returns 200A no-op is accepted and succeeds rather than reporting 'already in this stage'.
  • D-6 Removing an in-use close reason is allowedDeals keep the old code, which is reasonable, but the UI does not warn how many deals use it.

Checked and working

  • Delete guards: a stage with open deals, a pipeline with any deals, a company with references and the last active stage are all blocked with 409.
  • Deal state machine: won, lost and reopen enforce valid transitions; closed deals cannot move or close twice; three parallel 'won' calls give one 200 and two 409s.
  • Close reasons: outcome-specific, exact-code match, code format, 50-reason cap, duplicate code rejected.
  • Money: integer minor units, no negatives, safe-integer maximum, uppercase ISO currency.
  • Tenant isolation: another project's records return 404 for read, edit and delete; no session returns 401; bad project header returns 403; no data leaks through cursors or reports.
  • Pagination: signed cursors bound to resource and project; every tampered cursor returns 400; no duplicates or gaps at limits 1, 7, 25, 100.
  • Injection: XSS payloads in names and URL parameters never execute and are never reflected into the DOM; SQL, NoSQL and regex strings in search are inert; no open redirect through login ?next=.
  • Uploads: presigned S3 flow works; type allowlist and 25 MB cap enforced; filenames are labels only (ID-based storage keys).
  • Imports and exports: 1,500-row import OK; BOM, CRLF, quoted commas and newlines, unicode OK; per-row errors are accurate; 'reject' mode blocks duplicates; exported CSV neutralises formula cells and re-imports losslessly.
  • Resilience: offline submit keeps the draft and a retry makes exactly one record; acting on a record deleted in another tab shows a clear error; double-click on Create makes one pipeline; no layout overflow from hostile names at desktop or 375 px.
  • Dialog accessibility and keyboard: modal, labelled, focus trapped and restored; create works with keyboard only; behaviour matches in Chromium and Firefox (WebKit differs only in Safari's own focus rule).

Not tested

  • Member and other non-owner roles (only one account existed): permissions in Settings, member management, API keys.
  • Automation, Properties, Audit, Catalog products and Outbox beyond layout and accessibility checks.
  • Real screen readers (NVDA, VoiceOver, TalkBack) and Safari on macOS or iOS hardware.
  • Export file expiry after 7 days; load and performance testing (deliberately out of scope).
Most items above have an automated regression test in the crm-qa-suite folder; the rest (such as the truncated mobile table) were checked by hand. Known bugs are written as expected failures, so once one is fixed its test fails until the marker is removed. This report contains no credentials.
